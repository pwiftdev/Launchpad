# Code audit — 26 October 2026

Latest review and current release priorities: [27 October project audit](PROJECT-AUDIT-2026-10-27.md)
and [launch plan](LAUNCH-PLAN.md). This file retains the earlier findings/history; superseded
holder-payout and deadline proposals below are not the current product policy.

**The web deployment is prepared, but this is not approval for a real-money release.** The largest
unresolved issue is the gap between the advertised token economics and the available implementation.

Scope: current working tree, primarily `scaffolds/fun-launch`, public APIs, transaction
construction/submission, metadata/image processing, dependency lockfile, environment handling, and
deployment. Studio CLI and shared helpers received a targeted review. Existing uncommitted product
changes were preserved. This is a source review with automated checks, not a smart-contract audit,
penetration test, or review of cloud accounts and live on-chain configuration. No transactions or
private keys were sent to a network.

## Fixed in this change

| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **High: server-side requests to attacker-selected hosts** through on-chain metadata, anti-copy image hashing, and OG cards. HTTPS alone allowed private destinations, redirects, and unbounded bodies. | Central HTTPS gateway allowlist; no redirects or URL credentials; streamed byte limits; request timeout; bounded download concurrency/queue; bounded image pixels and image hash cache. Operator-configured gateway is a trusted destination.                                                                                                       |
| **High: unauthenticated Pinata spending** and weak runtime validation of upload requests. Arbitrary wallet strings did not prove ownership; invalid addresses were discovered after uploads.           | Validate all fields before work, including addresses, numeric types, UTF-8 name/symbol limits, 2 MB decoded images and actual image format. Remaining distributed abuse risk is listed above. |
| **Medium: transaction request logging and raw provider errors** could retain signed payloads or expose implementation details.                                                                         | Removed request-body logging, private signer request fields and commented server-signing code. Client errors are generic. Relay checks size, signatures and presence of a DBC instruction; it never signs transactions. This is not a full instruction-policy firewall.                                                                             |
| **Medium: malformed swap bodies and unsafe arithmetic** could crash handlers, permit invalid slippage or truncate sub-unit/overflow amounts.                                                           | Runtime schemas, finite positive amounts, safe integer base units, and integer slippage capped at 5%. | **Medium: no baseline abuse or framing protections.**                                                                                                                                                  | API request limits, JSON/content-origin checks for writes, no-store mutation responses, anti-framing CSP/X-Frame-Options, nosniff, referrer and permissions policies, production HSTS. ## Dependencies

The initial full-workspace registry scan reported **65 vulnerabilities: 5 critical, 31 high, 27
moderate and 2 low**. Updates to compatible versions of Next.js, sharp, Vitest and transitive
utilities, plus replacing the umbrella wallet package with the two adapters actually used, removed
hundreds of dependencies. Existing advisory suppressions were removed so upstream risks remain
visible.

The follow-up registry scan reports **13 vulnerabilities: 0 critical, 7 high, 5 moderate and 1
low**. These are registry findings in the workspace graph, not thirteen confirmed remotely
exploitable paths in the deployed app. Counts include tooling and studio; the standalone artifact
has a smaller traced dependency set. No complete runtime reachability analysis was performed.

| Package           | Remaining issue / constraint                                                                                                                                                                                                                                    |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `bigint-buffer`   | High native buffer-overflow advisory [GHSA-3gc7-fjrx-p6mg](https://github.com/advisories/GHSA-3gc7-fjrx-p6mg); registry reports no patched release. Local checks use the JS fallback. Do not enable its native build as a workaround for a performance warning. |
| `elliptic`        | Low advisory [GHSA-848j-6mx2-7j84](https://github.com/advisories/GHSA-848j-6mx2-7j84); no patched release in the scan.                                                                                                                                          |
| `image-size` 1.x  | Image-parser DoS advisories; fixed version is 2.0.3+, a major API change for React Native/Metro tooling. Not the server's sharp upload decoder.                                                                                                                 |
| `stream-json` 1.x | Parser/filter DoS advisories; fixed line is 3.6.0+, a major change underneath web3.js/Jayson. Do not force a major override without checking the consumer.                                                                                                      |
| `toml` 4.x        | Parser DoS advisories; fixed line is 5.0.1+, underneath Anchor. Requires compatibility verification.                                                                                                                                                            |

## Verification

Baseline: 21 existing tests passed. Added regression coverage for disallowed/internal metadata
hosts, redirect policy, response byte caps, signed launch payload tampering, origin binding,
expiry/replay, request limiting, Heroku forwarded-address handling, malformed swap bodies and
amount/slippage limits.

Completed locally:

- 47 app tests passed (21 existing plus 26 new cases).
- Four deployment environment validation tests passed.
- Web TypeScript checking and ESLint passed; inherited warnings remain visible.
- The optimized Next.js 15.5.28 production build passed on Windows, including type/lint checks and
  generation of all pages.
- Frozen-lockfile installation passed. Targeted tracked-text secret pattern scanning found no
  matches; local `.env` files are ignored. This was not a historical credential scan.
- JavaScript syntax checks and `git diff --check` passed.

Windows standalone packaging initially failed because the host disallows symlink creation. Windows
now uses normal Next.js output; Linux retains standalone output. The Linux artifact
packaging/startup and HTTP smoke checks are configured in `.github/workflows/ci.yml` but have not
run during the original audit. Automatic approval review rejected the attempted local preview server
startup with the reason "blocked by policy", so no local HTTP smoke test was completed. In the
subsequent deployment, Heroku's Linux standalone build and startup succeeded, and 23 live HTTP/API
checks passed on devnet. See [DEPLOYMENT.md](DEPLOYMENT.md).

Live wallet signing, Pinata uploads, real Solana transactions, cloud account permissions, DNS/TLS
and deployed program behavior require a devnet acceptance pass. No claim is made that the app cannot
be hacked.
